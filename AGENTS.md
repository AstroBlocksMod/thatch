# Thatch

## Overview

Thatch is an ahead-of-time compiler, written in Rust, that turns block-based programs into standalone native executables. It starts with Scratch 3.0 (`.sb3`) and is designed to grow to Snap! later. It is a real optimizing compiler, not an interpreter or a VM packaged with the project. License: Apache-2.0 with LLVM Exceptions (`Apache-2.0 WITH LLVM-exception`, see `LICENSE`). The exception matters here: runtime code that ends up inside a user's compiled executable does not force the Apache attribution terms onto that executable, so people can ship what Thatch builds under any license. Keep it that way. Use the SPDX expression above in every crate's `license` field, and be strict about what gets linked into output binaries (`thatch-runtime`, `thatch-abi`, anything they pull in). No copyleft there at all. Prefer licenses with no attribution requirement for binaries (Apache-2.0 WITH LLVM-exception, Zlib, BSL-1.0, 0BSD, Unlicense). MIT and BSD dependencies in the runtime would require users to ship their notices, so ask before adding one. The compiler itself can use any permissive dependency. Enforce this with `cargo deny` once it is set up.

The project is in its early stages. Much of what follows describes the planned design. When code lands that makes a section concrete, or changes it, update this file in the same change.

Goals, in priority order:

1. **Run vanilla Scratch exactly.** A standard `.sb3` must behave as it does in scratch-vm: same casting, same number formatting, same list and string quirks, same frame and thread timing. Speed never justifies a behavior difference.
2. **Native speed.** No browser and no JavaScript engine. Projects compile through a mid-level IR to machine code.
3. **Pluggable runtimes.** Compiled code talks to the outside world only through a versioned C ABI, so the same output can drive ScratchEverywhere (C++), other engines such as Project Tachyon, or a headless CLI runtime.
4. **Pluggable backends.** Codegen sits behind a backend trait. Cranelift first (fast builds), then LLVM (maximum optimization), with GCC possible later.
5. **A Scratch superset.** Later: compile-time macros, functions with return values, static types and FFI into the host engine, all while still loading every standard `.sb3`.
6. **Snap!.** Later still: first-class closures, anonymous functions and nested lists, added as a new frontend and new IR features, without rewriting the backends or the ABI.

### Planned layout

A Cargo workspace under `crates/`:

- `thatch-sb3`: reads `.sb3` archives and `project.json` into a typed project model. Keeps everything it does not interpret (unknown fields, raw inputs, extension data) so the project can be written back out unchanged.
- `thatch-values`: Scratch value semantics (cast to number, string and boolean, comparison, JavaScript number formatting, `Math` behavior). Shared by the optimizer (for constant folding) and the runtime. Must mirror scratch-vm's `Cast` and operator code exactly.
- `thatch-hir`: the block-level representation the frontend produces: scripts, hats, procedures, variables, lists, broadcasts. Language-specific (Scratch now, Snap! later).
- `thatch-ir`: the mid-level IR. SSA, typed (`f64`, `bool`, string handle, dynamic value, list handle), with explicit yield points for Scratch's cooperative threads. Language-neutral and backend-neutral.
- `thatch-opt`: passes over the IR (type inference, constant folding, inlining of non-warp procedures where safe, yield elimination in warp code, dead code removal).
- `thatch-codegen`: the `Backend` trait plus `thatch-codegen-cranelift` and later `thatch-codegen-llvm`.
- `thatch-abi`: the C ABI definitions (`#[repr(C)]` types and the function table generated code calls), with a header generated by cbindgen for C and C++ hosts.
- `thatch-runtime`: the Rust-side runtime linked into every executable: scheduler, value storage, lists, strings, and the glue between generated code and the ABI.
- `thatch-host-headless`: a minimal host for tests and benchmarks (virtual clock, prints `say` output, optional frame screenshots).
- `thatch-cli`: the `thatch` command.

Outside `crates/`: `samples/` (test projects as unzipped directories, zipped into `.sb3` by the build), `benchmarks/`, `docs/`.

### Rules that keep the layers separate

- The compiler never depends on `thatch-runtime`. Generated code only calls functions declared in `thatch-abi`. When you change an ABI function, update its declaration, the runtime implementation and every backend's call site together.
- The ABI is versioned. Any breaking change bumps the version, and hosts check it at load time.
- `thatch-ir` and the backends know nothing about Scratch or Snap!. If a backend needs to know what a block is, the IR is missing a concept.
- Language-specific lowering lives in the frontend (`thatch-hir` to `thatch-ir`), not in passes or backends.
- Superset features must not break vanilla projects. Store superset data so that the standard Scratch editor still loads the project, and keep a project that uses no superset features compiling exactly as a vanilla one.

## Scratch semantics (IMPORTANT)

- Read scratch-vm's source for every block you implement or optimize, and match it. Scratch's quirks are the spec: `"10" < "9"` rules, `NaN` handling, whitespace in numeric strings, `join` number formatting, list index parsing ("last", "random", "any"), case-insensitive comparisons and so on.
- A pass must keep the project behaving exactly as scratch-vm runs it. Document each pass and the conditions that make it safe in `docs/`.
- Thread timing matters: yields at the end of loops outside warp mode, the redraw request rules, broadcast-and-wait, `when I start as a clone`, and the 30 FPS frame. Get these wrong and many projects break even when every block computes the right value.
- jScratch (`../jScratch`, a Kotlin compiler for the same input) has worked through most of these details. Its SB3O library in `sb3o/` is BSD 3-Clause and can be ported here with its notice kept. Its other modules are GPL-3.0 and may only be ported if their copyright holder relicenses them. Never copy code from anyone else's GPL or AGPL project. scratch-vm, TurboWarp and ScratchEverywhere are references to read, not code to paste.

## Building and testing

- `cargo build --workspace` and `cargo test --workspace` once the workspace exists. Pin the toolchain in `rust-toolchain.toml`.
- End-to-end tests compile every sample, run it on the headless host and compare its `say` output with the expected output. Where possible, also check that output against scratch-vm in Node (differential testing). Every new block gets a sample.
- Snapshot tests (with `insta`) for the IR printed by each pass, so pass changes show up as reviewable diffs.
- Fuzz the value semantics against scratch-vm's JavaScript (`cargo fuzz` or a proptest suite fed by a Node oracle). Casting and number formatting are where bugs hide.
- After a change that could affect speed, run the benchmarks and compare with the previous results.

If your harness has dedicated search or file tools that already wrap these, those are fine too.

## Code Quality

Always lint and format:

- `cargo fmt --all` before committing. `cargo clippy --workspace --all-targets -- -D warnings` must pass.
- Configure lints once in the workspace `Cargo.toml` under `[workspace.lints]` and opt each crate in with `[lints] workspace = true`.

Use modern code practices:

- Latest stable Rust, edition 2024. Declare shared dependencies once in `[workspace.dependencies]`.
- `unsafe` only at the ABI boundary and in the runtime where it is actually needed, each block with a `// SAFETY:` comment explaining why it holds.
- Errors: `thiserror` in library crates, `anyhow` or `miette` only in the CLI. Compile errors shown to users should point at the sprite and block that caused them.
- No panics on bad input. A malformed `.sb3` is a reported error, not a crash.

## Keep things human

Do no use em dashes or other special symbols not normally found in writing. Do not word things in a weird way. Keep it looking human. If you need to use, for example, an arrow icon, use an SVG instead.

Replacing an em dash with a hyphen is NOT a fix. A spaced hyphen doing an em dash's job ("the limit - 4 bytes", "fast - but wrong") is the same tic with a different character. Reword the sentence instead: use a comma, a colon, parentheses, or the actual word ("minus", "to", "through"). Plain hyphens in compound words and numeric ranges like 0-1 are fine.
